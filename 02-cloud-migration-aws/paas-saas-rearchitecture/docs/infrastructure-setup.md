# Infrastructure Setup Notes — PaaS/SaaS Re-Architecture on AWS

Reference for how the VProfile stack was re-architected from the
lift-and-shift EC2 setup (see `../lift-and-shift-ec2`) onto AWS managed
services — same application, same multi-tier design, but every
self-managed EC2 service replaced with its managed equivalent.

## Migration Strategy: Rehost → Refactor

This is the second step in a two-part migration story:
1. **Lift and shift** (previous project) — move the app onto EC2 with minimal changes
2. **Refactor to PaaS/SaaS** (this project) — replace self-managed infrastructure with managed services to reduce operational overhead, improve scaling, and cut the team size needed to run it

| Self-managed (EC2, lift-and-shift) | Managed equivalent (this project) |
|---|---|
| Tomcat on EC2 + manual ASG/ELB setup | **Elastic Beanstalk** (bundles EC2, ASG, ALB, S3, CloudWatch into one service) |
| MySQL on EC2 | **Amazon RDS** (MySQL 8.0) |
| Memcached on EC2 | **Amazon ElastiCache** (Memcached engine) |
| RabbitMQ on EC2 | **Amazon MQ** (RabbitMQ engine) |
| Manual Route 53 private DNS entries | Not needed — Beanstalk/RDS/ElastiCache/MQ all provide managed endpoints |
| No CDN | **Amazon CloudFront** added for global content delivery |

## IAM Role for Elastic Beanstalk

Beanstalk's default auto-created role lacks permissions this project
needs, so a custom role is created manually with four policies attached:
- `AdministratorAccess-AWSElasticBeanstalk`
- `AWSElasticBeanstalkCustomPlatformforEC2Role`
- `AWSElasticBeanstalkRolesSNS`
- `AWSElasticBeanstalkWebTier`

This role is selected explicitly during Beanstalk environment creation
(Configure service access step) rather than letting Beanstalk generate
its own.

## RDS (MySQL)

- Custom **parameter group**: MySQL 8.0 family, DB parameter group type (not cluster)
- Custom **subnet group**: all subnets across all AZs in the default VPC
- Instance: `db.t3.micro` (free tier), MySQL 8.0.x, 20GB GP3 storage, storage autoscaling disabled
- **Not publicly accessible** — Beanstalk reaches it internally within the VPC
- Security group: the shared backend security group (see below)
- DB name: `accounts` (must match what the app expects)
- Password: auto-generated by RDS at creation time — captured once and stored, since RDS never displays it again (only reset, not retrieve)

**Database initialization**: RDS has no shell access, so a temporary
EC2 instance is launched in the same VPC purely to run the schema
import (`mysql -h <rds-endpoint> -u admin -p accounts < db_backup.sql`),
then terminated once the import completes. The temporary instance needs
its own security group with an inbound rule added to the backend
security group (port 3306 from the temp instance's SG).

## ElastiCache (Memcached)

- Custom parameter group: Memcached family, version 1.6
- Custom subnet group: same pattern as RDS
- Node type: `cache.t2.micro` (smallest available — cost control)
- 1 node (no cluster, this is a portfolio/demo scale)
- Port 11211 (must match `application.properties`)
- Security group: shared backend security group

## Amazon MQ (RabbitMQ)

- Single-instance broker (not cluster — cost control)
- Instance type: `mq.t3.micro`
- Engine: RabbitMQ 3.13
- Access type: **private** (internal VPC access only, no public endpoint)
- Security group: shared backend security group
- **Important**: Amazon MQ's AMQPS endpoint uses port **5671** (TLS), not
  5672 like a self-managed RabbitMQ instance — this must be updated in
  `application.properties` or the app cannot connect.

## Shared Backend Security Group

All three backend services (RDS, ElastiCache, Amazon MQ) sit in one
security group with:
- An inbound rule allowing all traffic **from itself** (so the three services can talk to each other)
- After Beanstalk is created, a second inbound rule is added allowing all traffic **from the Beanstalk EC2 instance security group** (not the load balancer security group — the instance one)

## Elastic Beanstalk Environment

- Platform: Tomcat 10 / Corretto 21 (Java 21)
- Configuration: **Custom** (not single-instance) — load-balanced, multiple instances
- Capacity: load-balanced, min 2 / max 4 instances, `t2.micro`
- Scaling trigger: **network out** (a strong signal for web app load — more users means more outbound traffic — alongside CPU utilization)
- Root volume: **GP3 explicitly selected** — defaulting to "container default" uses an outdated launch configuration and triggers a Beanstalk warning/error; GP3 forces use of a launch template instead
- Load balancer: Application Load Balancer, initially HTTP:80 → instance:80 (Beanstalk's Tomcat listens on 80, not 8080 like the manual EC2 setup)
- **Target group stickiness enabled** — same reasoning as the lift-and-shift project: this app has no shared session state
- Health check path: **`/login`** — the app redirects to `/login` by default, so the health check target must match or every instance shows unhealthy
- Health reporting: **Enhanced** — required for deployment policies that depend on per-instance health during rolling updates
- Deployment policy: **Rolling, 50% batch size** — with min 2 instances, this updates one at a time; chosen as a middle ground between "All at once" (fastest, full downtime) and "Immutable" (safest, most expensive — spins up a full parallel fleet before cutting over)

## Deployment Policy Comparison (for reference)

| Policy | Behavior | Trade-off |
|---|---|---|
| All at once | Every instance updated simultaneously | Fastest/cheapest, full downtime |
| Rolling | Fixed batch size or % updated at a time, old instances removed first | Some capacity reduction during deploy |
| Rolling with additional batch | New instances added *before* removing old ones | No capacity loss, extra cost during deploy |
| Immutable | Entirely new instance set created, cut over, then old set removed | Safest, most expensive, easiest rollback |
| Traffic splitting (canary) | New version gets a % of live traffic to validate before full rollout | Real-traffic validation, most complex to reason about |

## Build & Deploy Flow

Unlike the EC2 lift-and-shift project, there's no S3 push/pull step —
Beanstalk handles artifact storage and deployment directly:

1. Collect endpoints from RDS, ElastiCache, and Amazon MQ consoles
2. Update `application.properties` with those endpoints (and the Amazon MQ port fix: 5671)
3. Build locally: `mvn install`
4. Beanstalk console → **Upload and deploy** → select the `.war`, give it a version label, deploy
5. Beanstalk performs the rolling update per the configured policy, using target group health checks to gate progression between batches

## HTTPS & CloudFront

- ALB listener: HTTPS:443 added using the same ACM certificate from the lift-and-shift project, alongside the existing HTTP:80 listener
- **CloudFront distribution** created afterward, with the Beanstalk ALB as its origin, and the domain's DNS record is repointed from the ALB directly to the CloudFront distribution
- CloudFront settings: viewer protocol HTTP+HTTPS, all standard methods allowed, legacy cache settings forwarding all headers/query strings/cookies (broad forwarding — appropriate for a dynamic app, not a static site), all edge locations, alternate domain name matching the ACM certificate
- WAF **not enabled** here to stay in free tier — noted in the docs as something to enable in a real production setup
- Verified via browser dev tools: response headers show a `Via: <id>.cloudfront.net` entry confirming traffic is actually routed through CloudFront, not hitting the load balancer directly

## Known Gotchas

- **Amazon MQ port is 5671, not 5672** — easy to miss since the self-managed RabbitMQ project uses 5672; Amazon MQ's public/managed endpoint requires the encrypted AMQPS port instead.
- **Beanstalk Tomcat listens on port 80, not 8080** — unlike the manual EC2/Tomcat setup, so the ALB listener and health check both target port 80.
- **Health check path must be `/login`** — the default `/` path returns nothing meaningful for this app since it redirects immediately; leaving the default health check path makes every instance look unhealthy even when the app is fine.
- **Root volume type must be explicitly set to GP3** — leaving it as "container default" triggers a Beanstalk platform warning about outdated launch configurations.
- **RDS password is shown only once** — if the credential-view screen is closed before saving it, the only recovery option is resetting the password, not retrieving the original.
- **RDS has no public access and no shell** — schema initialization requires a temporary EC2 instance in the same VPC, deleted afterward.
- **CloudFront can't be deleted in one step** — it must be disabled first, wait for the distribution to leave "Deploying" state, and only then can it be deleted.
- **Security group cleanup ordering matters** — Beanstalk's own termination won't remove the manually-added "allow from Beanstalk SG" rule on the backend security group; that rule has to be removed manually before (or the backend SG will retain a dangling reference).
